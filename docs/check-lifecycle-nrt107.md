# Передача принятия и версий в DocCheck по NRT-107

Эти требования нужно согласовать с владельцем интеграции до изменения OpenAPI или схемы результата. UX-прототип использует синтетические наборы, хранит снимки версий в браузере и обрабатывает только имеющиеся подтверждения. [NRT-107](https://linear.app/andreiakimov/issue/NRT-107/sinhronizirovat-izmeneniya-interfejsa-andreya-s-doccheck).

## API и состояния

| Операция | Предлагаемый контракт |
| --- | --- |
| Создать исходную проверку | Сохранить `POST /api/v0/runs`, `Idempotency-Key`, `202` и `Location`. Внутри зарегистрировать логическую проверку и версию 1. Старый клиент продолжает работать по `run_id`. |
| Прочитать версии | `GET /api/v0/checks/{check_id}/versions` возвращает номера, время создания, `parent_version_id`, `run_id`, статус задания, признаки текущей версии и принятия, ссылку на состав. Результат и доказательства адресуются через существующие представления конкретного `run_id`. |
| Принять версию | Идемпотентный `PUT /api/v0/checks/{check_id}/versions/{version_id}/acceptance`. Доступен для `completed` и `completed_with_issues`. Сервер фиксирует `accepted_at` и `accepted_by` из аутентифицированного контекста. Незавершённая версия получает `409`, повтор возвращает исходное решение. Финансовые данные остаются доступными в исходном виде. |
| Читать активные и архивные | `GET /api/v0/checks` с параметром `view=active` или `view=accepted` и существующим подходом к пагинации. В активной выборке текущие непринятые результаты и незавершённые задания. В принятой выборке все принятые версии. Фильтр «Приняты» и архив используют ту же выборку, ссылки содержат ID версии. |
| Изменить комплект | `POST /api/v0/checks/{check_id}/versions` с `base_version_id`, `expected_current_version_id`, сохранёнными ID документов родительской версии и файлами для добавления или замены. Не включённые в новый состав файлы исключаются из новой версии. Выбранные файлы из другой проверки не принимаются. При повторной отправке того же запроса применяется прежний `Idempotency-Key`. Успех возвращает `202`, `version_id`, `run_id` и `Location`. При несовпадении `expected_current_version_id` с текущей версией или при уже выполняющемся запуске сервер возвращает `409` с фактическим состоянием. `base_version_id` может указывать на любую завершённую версию этой проверки, включая историческую. |

Назначение очередного номера версии, создание задания и фиксация состава выполняются в одной транзакции. Ограничение разрешает только один запуск в состояниях `queued` и `processing` на проверку. Пока версия `queued` или `processing`, текущим остаётся последний завершённый результат. Успешное завершение атомарно обновляет текущую версию. При `failed` прежний результат остаётся текущим, а новая попытка видна со статусом ошибки и возможностью повторить. Новая версия начинается непринятой. Для принятия в интегрированном продукте нужен аутентифицированный пользователь и проверка его доступа. Ограничения публичного демо для `/api/v0/runs` распространяются и на `/api/v0/checks`.

## Прогресс загрузки и обработки

- Сохранить канонические статусы задания. Подробный этап передавать отдельно и только из фактического события обработчика, например `reading`, `extracting`, `matching`, `concluding`.
- Дать UI необязательные `documents_processed`, `documents_total`, `progress_percent` и `updated_at`. Процент берётся из `progress_percent` или из доступного отношения числа обработанных документов к общему числу. Если обоих сигналов нет, клиент показывает этап с неопределённым прогрессом. Для HTTP-загрузки браузер измеряет переданные байты отдельно от обработки.
- Успешный результат должен иметь стабильную ссылку. Ошибка содержит код и пользовательское описание. Повтор запросов использует исходный идемпотентный ключ, восстановление страницы читает последнее состояние серверного задания.
- Отдавать подтверждённый номер КФЗ отдельно от ID запуска. Для каждого документа сохранять исходник, состояние чтения, причину исключения и ссылки на показатели и доказательства. По документу из исключений должна открываться доступная страница оригинала.

## Хранение и миграция

- `checks`: логический ID, область доступа и ссылка на текущую завершённую версию. `check_versions`: ID, `check_id`, номер, родитель, `run_id`, время создания и ссылки на неизменяемый состав и результат. Ограничения уникальности по `(check_id, version_number)` и `run_id`.
- `version_documents`: снимок порядка, роли, заголовка и ключа исходного файла. Замена создаёт новый ID документа. Исключение убирает привязку только из нового состава. Исторические ссылки на файлы и доказательства сохраняются.
- `version_acceptances`: одна запись на версию, время и пользователь. Индексы для активного списка, архива и выборки обновлений задания. Проверка полномочий применяется и к истории, и к запросам файлов.
- Добавить таблицы и nullable-ссылки, заполнить версию 1 для уже сохранённых заданий и перепроверить результат и адреса источников по существующему `run_id`. Проставить текущую версию для завершённых результатов. Существующие выводы о достоверности не превращать в принятие. После проверки заполнения включить ограничения и новые операции. Старые запросы продолжают читать те же результаты.

## Кеш извлечения

Сервер вычисляет SHA-256 по байтам сохранённого файла. Ключ совместимости включает версию извлекателя и модели OCR, формат схемы результата извлечения и отпечаток существенных параметров в канонической форме. Доступ к сохранённым результатам ограничен областью хранения и правами проверки. Кеш хранит извлечённые поля и их адреса, а не финансовое решение.

Совместимая запись для неизменившегося файла может использоваться в новой версии. При отсутствии записи, изменении файла, версии обработчика или параметров worker запускает извлечение. При сбое кеша обработка может идти напрямую. Интерфейс показывает только фактическое состояние, подтверждённое worker. Проверки связей, полноты и финансовая сверка выполняются для каждого нового состава.

## Приёмка интеграции

1. Принять версию с расхождениями и открыть её по ссылке из архива. Сверить исходные статусы, суммы и адреса источников.
2. Запустить изменение принятой версии. Во время обработки открыть предыдущий результат. После успеха открыть новую непринятую версию, затем переключиться назад. Проверить reload, архив и прямую ссылку на документ.
3. Повторить запрос с тем же ключом и отправить конфликтующее изменение. Проверить, что создаётся одна версия и что неуспешный запуск оставляет доступным прежний результат.
4. Проверить переиспользование после неизменного файла, промах после изменения содержимого, инвалидирование после изменения обработчика, отказ кеша и повтор финансовой сверки во всех случаях.
5. Зафиксировать диапазон коммитов Андрея и сопоставление компонентов в отдельном интеграционном PR по NRT-107. Сохранить интерфейс действующего API для клиентов, маршруты доказательств и финансовые тесты.
