# Продуктовые решения DocCheck

DocCheck помогает главному бухгалтеру и его заместителям проверить КФЗ по первичным документам, понять происхождение суммы и открыть подтверждающий фрагмент. Ветка `main` репозитория `ananakimov/project-placeholder` задаёт дизайн и пользовательские сценарии.

## Реализовано в UX-прототипе

| Сценарий | Поведение |
| --- | --- |
| Навигация | «Новая проверка» и «Проверки». На широком экране меню свёрнуто до значков и раскрывается поверх страницы при наведении, фокусе или нажатии. На телефоне доступна кнопка меню. |
| Список проверок | Колонки «Проверка», «Результат», «Покрытие по сумме», «Документы», «Дата». Строка открывается целиком и сохраняет ссылку для перехода с клавиатуры. Новые задания выше, при совпадении времени порядок задаёт ID. У готовых примеров есть календарная дата. При наличии извлечённого номера отображается «КФЗ №…», иначе «Проверка КФЗ №…» с идентификатором запуска. |
| Фильтры | «Все» включает готовые примеры и демо-задания. «Есть расхождения» и «Неполные данные» могут включать один результат одновременно. «Без расхождений» требует подтверждения всех применимых показателей. Состояние задания не даёт финансового статуса. Синтетика маркируется один раз для целиком демонстрационной выборки или у конкретной проверки в смешанном списке. |
| Несколько комплектов | В форме один КФЗ и список первичных документов. После добавления комплекта форма очищается. «Последние демо-задания» и общий список показывают названия, время и состояния. В браузере хранятся метаданные до 50 заданий. Симуляция очереди и обработки не читает документы и не создаёт новых результатов. Кнопка «Загрузить пример» открывает подготовленный результат с оригиналами синтетических файлов. |
| Результат | Заключение о достоверности и общая рекомендация вверху. В одной карточке покрытия видны сумма, доля и количество по статусам. Рублёвые значения берутся из результата. Неденежные и служебные показатели не увеличивают рублёвое покрытие. |
| Таблица и расчёт | Шесть колонок «Показатель КФЗ», «В КФЗ», «Ожидаемо», «Разница Δ», «Статус», «Пояснение». В раскрытии видны документы и слагаемые при известном основании, исключения, значения и частичные подтверждения. Неизвестное значение отображается прочерком. Возможные причины вынесены в раскрываемый список. |
| Правая панель | Клик по документу открывает просмотрщик и записанный фрагмент. На широком экране таблица и источник доступны одновременно, на телефоне источник располагается над таблицей. Глазик сворачивает и возвращает выбранный документ, его страницу, масштаб и подсветку. Поддерживаемые адреса берутся из фактических данных источника. |
| Дополнительные проверки | После таблицы показаны имеющиеся исключения, состояние проблемных файлов и недостаточные подтверждения. Доступные источники открываются по ссылке. Исключённый дубль сам по себе не образует финансового расхождения. |

## Утверждено, не реализовано в UX-прототипе

- **Серверная очередь и история.** Передать один КФЗ и комплект первичных документов по существующему API. После подтверждения сервером очистить форму и отобразить стабильный идентификатор, время создания и состояние. Идентификатор и состояние должны восстанавливаться из API при повторном открытии. Предотвращение повторной отправки должно опираться на подтверждение приёма задания. Показывать передачу файлов отдельно. Состояния API `queued / processing / completed / completed_with_issues / failed` соответствуют «В очереди», «Обработка документов», «Готово», «Готово с замечаниями» и «Ошибка обработки». При наличии счётчиков показывать число обработанных документов. Проценты загрузки и отдельный этап «Сверка» доступны при наличии соответствующего сигнала. Для обоих успешных состояний показывать ссылку на доступный результат.
- **Принятие и архив.** Бухгалтер завершает работу с результатом явным принятием. Это состояние учитывается отдельно от достоверности и обработки. Ожидаются серверные поля принятия, время и пользователь, операция принятия и чтение списка по единому состоянию для «Приняты» и «Архив проверок». Принятая проверка переходит из «Все» в «Приняты» и архив. Задания с технической ошибкой остаются в общем списке до явного решения бухгалтера. Исторический результат остаётся доступен.
- **Изменение комплекта и версии.** Добавить, заменить или исключить документ и запустить повторную проверку. Нужны создание версии, чтение списка и выбор исторической версии. Для версии требуются ID исходной проверки, номер, время создания, состав комплекта, связь с предыдущей версией, результат и доказательства. Прошлые результаты сохраняются вместе с адресами источников.
- **Повторное использование OCR.** Ключ совместимости включает SHA-256 файла, версию извлекателя и существенные параметры. Совместимые результаты можно переиспользовать. Изменённые файлы распознаются заново, несовместимый кеш инвалидируется. При изменении состава сервер повторяет проверки связей, полноты и финансовые вычисления.

## Гипотезы

Гранулярные стадии и проценты после передачи файлов зависят от сигналов worker. Формат структурного адреса для листов и текстовых документов зависит от извлекателя и просмотрщика. Для принятия и версий названия операций и наборы полей подлежат согласованию с владельцем интеграции.

## Перенос через NRT-107

Цепочка **репозиторий Андрея → проверка изменений в main → адаптация в PR интегрированного DocCheck**. Обратный перенос визуальных компонентов требует отдельного согласования. [NRT-107](https://linear.app/andreiakimov/issue/NRT-107/sinhronizirovat-izmeneniya-interfejsa-andreya-s-doccheck).

1. Зафиксировать диапазон коммитов UX относительно последней интеграции. Сопоставить изменения с текущими `main` и PR №82–84 интегрированного приложения, чтобы переиспользовать существующую реализацию и тесты.
2. Сопоставить состояние очереди, даты и доступность результата с действующими API. Сохранить сырые канонические статусы, точные суммы и `null`. Для формул отображать известные слагаемые и итог из результата. Не считать неполные или неоднозначные источники полным подтверждением.
3. Сохранить существующие источники и адреса доказательств, включая номер страницы и bbox или доступный структурный адрес. Формат данных проверять по техническим контрактам, UI адаптировать под источники, которые действительно доступны.
4. Указать диапазон, допущения, результаты UI и API-проверок в интеграционном PR. Техническая архитектура, сценарии К6, README и контракты интеграции ведутся в [VCyberPunk2077/doccheck](https://github.com/VCyberPunk2077/doccheck).
