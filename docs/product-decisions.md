# Продуктовые решения DocCheck

Ветка `main` репозитория Андрея задаёт UX DocCheck. Здесь описаны сценарии и поведение интерфейса. Техническая документация интегрированного приложения находится в [VCyberPunk2077/doccheck](https://github.com/VCyberPunk2077/doccheck) и описывает фактически подключённые API, OCR и правила сверки.

## Что показывает прототип

| Сценарий | Поведение |
| --- | --- |
| Новая проверка | Бухгалтер выбирает один КФЗ и комплект первичных документов. После отправки формы очищаются для следующего комплекта. Очередь, имитация обработки и завершение маркированы как демонстрация. Браузер хранит номера, время и количество документов для 50 последних демо-заданий. Содержимое файлов не отправляется и не сохраняется приложением. |
| Готовый пример | Открывается отдельной кнопкой с меткой «Синтетика». Для КФЗ №3/7 в комплекте за 2027 год доступны страницы из исходных файлов примера и проверенные области подсветки. |
| Проверки | Поиск по названию и договору, сортировка по дате или названию. Фильтры «Есть расхождения» и «Неполные данные» могут включать один результат одновременно. «Без расхождений» показывает полностью подтверждённые проверки. Счётчики относятся к готовым примерам. «Все» также показывает отдельную историю демо-заданий. |
| Результат | В одном блоке видны число показателей, сумма и доля по статусам. Денежные суммы берутся из покрытия проверки. Вложенные и служебные строки не увеличивают счётчики. В таблице видны КФЗ, сумма по источникам, разница, статус и объяснение. |
| Источник | Раскрытие строки показывает документы, слагаемые и рекомендации. Клик по документу открывает соответствующий источник с подсветкой. Закрытие возвращает к раскрытой строке. Сохраняются переходы между документами, масштаб и разворот на весь экран. |
| Дополнительные проверки и заключение | После таблицы видны исключённые документы, ошибки чтения и недостаточные подтверждения с причинами и известными частичными суммами. Затем показан вывод проверки. Локальные отметки просмотра, комментарии и подпись сохранены как сценарии прототипа. |

## Что требует backend

- Реальная отправка комплектов, постоянные идентификаторы заданий, очередь, обработка OCR и получение статусов, результатов и истории из API. Эти сценарии реализуются в интегрированном репозитории. Демо-задание в прототипе заканчивается статусом симуляции без результата сверки.
- Ошибки чтения и причины статусов для новых комплектов, реальные файлы и координаты подтверждений приходят из интегрированного приложения. Работа над ML-адаптером продолжается отдельно.
- Применимость сохранения пользовательских решений на сервере и формального принятия результата требует отдельного согласования. Действия прототипа не меняют рабочий процесс интегрированного MVP.
